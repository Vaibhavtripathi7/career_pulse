## Workload

- **100,000 unique synthetic messages** across 1,000 users (100 each), plus **5,000 exact duplicates** (same ID, same content) = **105,000 Gmail deliveries per run**.
- 10,000 job-application emails (10%) and 90,000 promo/other emails, from 17 templates. Message IDs are stable 16-hex strings.
- One BullMQ job per user, which is production's unit of work (`fetchemails(userId)`): 1,000 jobs per run. Each worker process runs production's worker unchanged, with concurrency 2.
- Production code is not modified. `googleapis` and the Gemini fallback are swapped for local fakes by ESM resolve hooks, and any non-loopback TCP connection is refused. `NODE_ENV=production`: pino JSON logs at info (to /dev/null) and Postgres over TLS.
- **Oracle:** the production parser, run over every unique message, accepts **9,875** of them, so that is the exact row count a complete sync must produce. It stores 9,875 of 10,000 job emails and 0 of 90,000 promos. It predicts **283 LLM-fallback calls per pass** (265 unique messages, re-parsed when duplicated).
- **Single-threaded pipeline cost** (parser + body extraction, no queue or database): 44 µs per message, 22,596 msgs/s. Generating the synthetic source costs another 25 µs per delivery, which the workers also pay.

## Analysis

<!-- ANALYSIS:START -->
### Where it stops scaling

Going from 1 to 2 workers gives 1.55x, 2 to 4 gives another 1.35x, and 4 to 8 gives nothing (0.97x, and the run-to-run ranges overlap). **Throughput tops out at about 8,600 messages/s with 4 worker processes (8 jobs in flight).** Going to 8 processes only doubles job latency (p50 from 90 to 174 ms).

### The bottleneck is CPU

| Worker processes | Messages/s | Worker CPU per delivery | Fake-source CPU per delivery (fixed work) | Clock of busy cores | Machine CPU busy | CPU per worker |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 4,116 | 203 µs | 29 µs | 2,481 MHz | 24% | 83% |
| 2 | 6,384 | 279 µs | 39 µs | 2,328 MHz | 38% | 85% |
| 4 | 8,640 | 443 µs | 61 µs | 1,844 MHz | 71% | 93% |
| 8 | 8,381 | 640 µs | 132 µs | 1,698 MHz | 96% | 68% |

Medians of the three runs from `results/latest.json`. CPU per delivery is worker CPU seconds divided by the deliveries processed.

1. **The workers are CPU-bound.** Up to 4 processes, each one keeps 83-93% of a core busy. The rest of the time it waits on Postgres and Redis.
2. **The same code costs more CPU per message as workers are added:** 203 µs with 1 worker, 640 µs with 8. The fake Gmail source does exactly the same work in every run, and its cost still went from 29 to 132 µs per delivery. So the CPU is getting slower; the code isn't doing more.
3. **There are two reasons.** First, the clock of the busy cores falls from 2.48 to 1.70 GHz as more cores load up. This is a 15 W laptop chip; one busy core boosted to about 3.4 GHz when I checked. Second, past 4 physical cores, processes share cores through SMT. At 4 workers the demand is already about 4.5 cores: 3.73 for the workers, 0.65 for Postgres, 0.10 for Redis and 0.06 for the runner.
4. **At 8 workers the machine is out of CPU.** It is 96% busy, and each worker only gets 68% of a CPU because it is waiting for a free core. Throughput stays flat and latency doubles.
5. **The code itself shows no contention.** The CPU profiles (`results/profile-summary.md`) split worker CPU almost the same way at 1, 4 and 8 workers: Prisma and pg 30-32%, sync code 18-22%, test harness 16-18%, parser 9-10%, logging 7-8%, BullMQ and ioredis 1-2%. Only Node's own runtime share grows (4.5% to 9.5%), and that includes process startup. Nothing points at a lock, a queue or the connection pool.

Postgres and Redis are not the limit:

- **Postgres** used 0.25-0.77 of a core, with exactly 2 connections per worker process (one per job in flight, all over TLS). That is 16 at 8 workers, against a pool limit of 10 per process and Postgres's 100.
- **Redis** used 0.05-0.12 of a core: 39-40 commands per job, about 3,200 commands/s at peak.
- **Memory** caused no swapping (swap stayed around 1.6 GB). But 8 workers at 360-450 MB each brought free RAM down to about 1.5 GB, so more processes wouldn't fit well on this laptop anyway.

### Where worker CPU goes (1 worker, 19.8 s busy)

- **Prisma and pg, 32%:** about 6 ms of CPU per job for 4 small queries. Those are loading existing applications, loading the user, a `createMany` of about 10 rows, and the `lastSyncAt` update. Much of it is Prisma 7's WebAssembly query compiler, and it is more than the parser costs.
- **Sync code, 22%:** `gmail.ts` and its helpers. The hottest function is `htmlToText` in `extractEmailBody`, which turns promo HTML into text.
- **Parser, 10%:** 44 µs per message on one thread (22,600 messages/s).
- **Logging, 8%:** pino writes two info lines for every ignored email, one in `parsers/index.ts` and one in `gmail.ts`.
- **Test harness, 17.5%:** the fake Gmail source and IPC. Without it, a worker would get roughly 20% more done.

**What would raise the ceiling:** more cores first, since the workers are stateless and Postgres and Redis had plenty of room at peak (0.65 core, 8 connections). After that, less CPU per job: the ORM is the biggest single cost, and logging every ignored email takes 8%.

### The sync latency metric is too coarse

The lowest bucket of `email_sync_duration_seconds` is 0.5 s. In every run, all 1,000 jobs at 1-4 workers fell into it, and 995-997 of 1,000 at 8 workers. So `histogram_quantile` reports 250 / 475 ms at every load. That is just interpolation inside 0-0.5 s, while the real p50 is 48-174 ms. Seeing sync latency would need buckets from about 10 ms to 250 ms.

### Kill test

- **Setup:** 3,000 jobs (the same 1,000 users queued three times at once) on 4 workers, with one SIGKILL about every 5 s, 18 in total. The first 6 kills came in the first 33 s, while work was still running, and each one interrupted 2 jobs. The rest hit idle workers.
- **Recovery:** all 12 interrupted jobs were retried and finished. Their locks ran out after 30 s, BullMQ's stall check put them back in the queue, and another worker picked them up. No job failed.
- **Database: 9,875 / 9,875 rows, 0 missing, 0 extra, 0 duplicates.**
  - **No duplicates,** even though every mailbox was synced 3 times (2.99x the work and about 849 LLM fallback calls, which is 3 x 283). The unique key on `(userID, messageId)` plus `createMany` with `skipDuplicates` absorbs the repeats.
  - **Nothing lost,** because `fetchemails` writes once at the end of a job: a killed job writes nothing and its retry writes everything.
- **Drain time** was 98 s, against about 12 s for a normal 4-worker run. About 36 s of that is the tripled work; the rest is waiting for the stalled locks to expire.
- **The failure case exists but didn't come up here.** BullMQ 5.81 allows one stall per job (`maxStalledCount: 1`). A job killed twice gets a deferred failure ("job stalled more than allowable limit") and fails on its next pickup without a retry, because `attempts: 3` only covers thrown errors (`moveStalledJobsToWait-9.lua`, `Worker.getUnrecoverableErrorMessage`). An early smoke run on a busy machine, which wasn't kept, hit this twice. The data was still complete, because the same users' other jobs succeeded.
  - A saved run with a kill every 1.5 s (`results/adversarial-aggressive.md`: 40 kills, 50 users) passed without hitting it, since that small workload finishes before any job can be killed twice.
  - In production the next cron run covers it, because `lastSyncAt` only moves after a clean sync.

### Limits this test doesn't cover (from reading the code)

- **Gemini fallback:** limited to one call every 6 s per process (`CALL_INTERVAL_MS`). This workload makes 283 calls per pass, which takes at least 28 minutes per process, against about 25 s for everything else. **With a real LLM, the fallback is the ceiling, not the CPU.**
- **Gmail API:** every message is a `messages.get` round trip, with at most 2 in flight per process (the module-level `pLimit(2)` in `gmail.ts`).
- **Cron enqueue:** it sleeps 1 s per user inside a 10-minute timeout (`cron.ts`). Above roughly 600 users the timeout fires, and `runWithRetry` starts a second enqueue loop while the first is still going, so a user can be queued up to 3 times. The kill test shows the data stays correct when that happens, but the work triples.

### Caveats

- This is a laptop, not a server. The 1-minute load average was 2.86 at the start. The 5- and 15-minute averages were still high from a CPU-heavy process stopped just before.
- The first full run was slowed by a busy browser and showed scaling stopping at 2 workers. It is kept as `results/run1-browser-contended.json`, and it is why this run was done with the machine idle.
- The fake mail is HTML-heavy (90% promo). In production, Gmail's search query drops most promos before the worker sees them, so the real cost per message will differ.
- The fake Gmail source runs inside the workers and counts toward their CPU (about 17%).
